# Разбор серверного spark: 2.10.1 → 2.10.3

## Источники и метод

- Старый: `eternal-snow-1.20.1/v2ztefdt8G.sparkprofile`, Git blob `c3df0d2b540830a62ef2ec969633e86b4f2a4b99`.
- Новый: `TnflFsCayi.sparkprofile`, Git blob `156da3b085a921824d4d2853ea0f52444fc0b17c`.
- Разобраны protobuf SamplerData по схеме lucko/spark. Версии мода проверены в metadata.sources: 2.10.1 и 2.10.3.
- Проценты ниже — семплы выбранного Server thread, а не загрузка всех CPU. Включают дочерние вызовы; вложенные проценты не складываются. Рекурсивные вызовы одного метода не суммируются повторно поверх самих себя.
- Это два наблюдения, не контролируемый A/B-бенчмарк. Старый профиль: 1 игрок/213 сущностей; новый: 0 игроков/119 сущностей на момент итоговой сводки. Нельзя приписать все отличия одному изменению кода.

## Что сработало

Полная пересборка больше не попала в семплы этого прогона. Это не означает, что код
rebuild удалён или никогда не выполнится: он остаётся для первой сборки, смены
материальных настроек и компактации после выгрузки непустых чанков.
Локальные обновления занимают 4576 ms из 119828 ms семплированного потока (3.819%).
Около 3384 ms внутри них — три ветки Arrays.copyOf: адаптер всё ещё копирует массивы
до точного размера при росте, в отличие от геометрического роста численного ядра.

## Главный оставшийся расход

CellHeatSolver.step занимает 72800 ms (~60.75%). Из них собственное время метода
69680 ms (~58.15% всего потока), Arrays.fill — ещё 3108 ms. Это уже преимущественно
арифметика и обход массивов/объектов рёбер, а не построение графа или поиск тегов.
Распределение по двум окнам стабильно: 36340 и 36460 ms — не разовый стартовый всплеск.

Связь с кодом:
1. Для шага 0.5 s рассчитывается минимальный устойчивый подшаг для всего графа.
2. Каждый подшаг снова проходит все рёбра и все ячейки.
3. Усиление перемешивания воздуха из 2.10.2 увеличивает суммы проводимости и число
   подшагов. Для однородной внутренней воздушной ячейки с шестью соседями, C=1:
   при G=1 нужно ceil(0.5/(0.9/6))=4 подшага, при G=3 — 10.
   Это пример из формулы, НЕ измеренное число подшагов в профиле пользователя.
4. Один быстрый участок задаёт подшаг и для массивных стен, которым такой частый
   пересчёт может не требоваться. Состояние хранится глобально по измерению.

Профиль не содержит числа тепловых ячеек, рёбер и фактических подшагов. Нельзя
объявить увеличение конвекции единственной причиной роста стоимости step.
Осталась также неконтролируемая по общему размеру область расчёта: frontier добавляет
ячейки при отличии от текущей наружной температуры, в том числе из-за смены погоды,
а не только возле огня. Это риск роста по коду, не измеренный объём в данном файле.

## Обход Minecraft и проверки

- computeBaseAmbientC: 5.244%, 6284 ms — время суток/небо и вычисления окружения.
- ready: 5.234%, 6272 ms — повторные проверки загруженности и высоты мира.
- isAirOrOpenPassage: 1.325%, 1588 ms — в том числе collision shape.
- seed: 1.105%, 1324 ms.
- SeekWarmthGoal.canUse: 0.037%, 44 ms. ИИ поиска тепла не главный источник задержки.
- SnowAccumulationManager.tickLevelSnow: 0.020%, 24 ms. Этот профиль не обосновывает
  отключение снегопада как основное лечение.

Имеются готовые w.air и свойства материалов; повторно спрашивать форму блока в
ежешаговом цикле не требуется, если инвалидировать кэш при изменении состояния.
Проверку загрузки можно группировать по чанку. Наружную температуру для G=0 можно
не рассчитывать: этот член уравнения равен нулю. Для остальных необходима корректная
инвалидация по погоде/времени и изменению крыши; нельзя кэшировать навсегда.

## Память и масштаб мира

На момент сводки heap used ~858 MiB, committed ~1246 MiB; Xmx=3 GiB.
Platform GC: 24 young collections, avg 10.625 ms, avg frequency 5341 ms;
в старой platform-сводке 89, avg 91.921 ms. Это агрегаты spark, не покадровая
атрибуция пауз всей записи. Данных за OOM как основную причину здесь нет.

Оба минутных окна нового профиля: 2209 чанков, 119 сущностей. В server.properties
view-distance=10, simulation-distance=10. Число чанков не равно числу тепловых ячеек.
Нельзя из этих данных заключить, что все чанки активно тикают или удерживаются
именно модом; загрузка спавна/билеты требуют отдельной проверки.

## Следующая работа по приоритету

1. Добавить диагностические счётчики размера графа, рёбер, подшагов, роста и времени
   фаз. Иначе оптимизация step выполняется вслепую относительно размера задачи.
2. Оптимизировать численное ядро: плотные примитивные массивы рёбер вместо объектов,
   убрать лишние полные проходы/заполнение неиспользуемой ёмкости. Измерять на G=3,
   а не только старых тестах с G=1.
3. Рассмотреть локальные подшаги или иной устойчивый интегратор. Это изменение
   численного метода, требующее тестов энергии, отсутствия выбросов, одинакового
   физического времени и паузы выгруженных областей; нельзя просто обрезать подшаги.
4. Убрать повторные запросы мира там, где уже есть валидный кэш; увеличить массивы
   адаптера геометрически, сохраняя отдельное число реально активных ячеек.
5. Отдельно проверить рост активного графа при смене погоды и простое без игроков.
   Не удалять температуры и не замедлять тепло ради красивого TPS.

Итог: 2.10.3 исправила пересборку как главный расход старого профиля, но общий расчёт
остаётся неприемлемо тяжёлым. Данный документ — анализ; новой исправленной сборки
в рамках этого разбора нет. 20 TPS пока не подтверждены.
